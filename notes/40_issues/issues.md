## 1. 検証

### **未** i260927-01 並列スロットのスループット実測

階層型エージェント構成案の Phase 1。`--parallel` で同時に投げたとき、合計の生成速度が単発の何倍になるかを測る。 帯域律速のため N 倍にはならない見込みで、1.3 倍未満なら並列を諦めて逐次実行の構成に単純化する。

- **未** `--parallel 1 / 2 / 4` で同時リクエストを投げ、合計 tok/s と VRAM 使用量を測る
- **未** 結果を構成案に反映し、並列の採否を決める

関連: [階層型エージェント構成案](../10_plan/p260825-01-階層型エージェント構成案.md)

### **未** i260927-02 Speculative Decoding の検証

小さなドラフトモデルで先読みして生成を速める手法。本命とドラフトを同居させると VRAM の余裕は約 200 MiB と見積もっており、 帯域を使い切っている本PCでは効果が出ない可能性もある。

- **未** 使用中のビルドの `llama-server --help` で、ドラフトモデル指定のオプション名を確かめる
- **未** 本命と同系列のドラフトモデル（Qwen3-0.6B の GGUF）を取得する
- **未** 調査の検証計画にある5構成を測り、結果を調査に反映する

関連: [Speculative Decoding 調査](../01_research/r260825-01-投機的デコーディング.md)

### ⚠ **着手** i260927-05 RAM 32GB を前提に結論を見直す

RAM を 32GB に増設し、画面表示を内蔵GPU に任せたところ、CPU 側に重みを置くモデルが大きく速くなった （Qwen3.5-9B 8.1 → 14.6 tok/s、gpt-oss-20b 5.9 → 19.0 tok/s）。KV を q8_0 にすればコンテキスト 16384 も使える。 実行計画の結論と方針は RAM 16GB の実測に基づいたままで、再測定と合わなくなっている。

- ✅ **済** RAM と VRAM に左右されるものを 32GB で測り直し、実行計画・調査に追記する
- **未** 実行計画の結論と方針（gpt-oss-20b の位置づけ、コンテキストの上限）を見直す
- **未** gemma-4-E4B を測り直す（CPU 側に置く PLE が速くなる可能性がある）
- **未** Qwen3-30B-A3B（Q4_K_M・約 18 GB）を取得して測る
- **未** Claude Code 用のモデルを gpt-oss-20b で試す（Qwen3-4B でツール呼び出しが成り立つかは未確認）

関連: [ローカルLLM 実行計画](../10_plan/p260824-01-ローカルLLM実行計画.md)（第10章の「32GB での再測定」）

## 2. 運用

### ✅ **済** i260927-03 Claude Code の接続先を llama-server へ切り替える

これまで LM Studio に向けていた接続先を、llama-server（`127.0.0.1:8080`）へ切り替える。 llama-server は Anthropic 形式の `/v1/messages` に直接応答するため、変換の層を挟まずに繋がる。

Claude Code は最初の要求だけで約 63,000 トークンある。VRAM 4GB には KV キャッシュが載らないため、 コンテキスト 65536・KV キャッシュを RAM 側（`-nkvo`）・q8_0 で起動する。 初回は 157 秒かかるが、2回目以降は共通部分が再利用されて 14 秒になる。

- ✅ **済** llama-server が Anthropic 形式に直接応答することを確かめる
- ✅ **済** サーバの起動（`tools/50_run/run-server-cc.cmd`）と Claude Code の起動（root の `cc1.cmd`）をスクリプトにする
- ✅ **済** Claude Code から応答が返ることを確かめる

関連: [ローカルLLM 実行計画](../10_plan/p260824-01-ローカルLLM実行計画.md)（導入手順の Step 5）
